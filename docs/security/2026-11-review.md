# Security, load and design review: November 2026

- **Scope:** everything built up to PR #358: API foundation, workspaces/RLS, sign-in, WhatsApp provider layer, scale foundations, permissions, API conventions. Plus the infrastructure plan (ADR 0010, ADR 0011).
- **Method:**
  1. White-box code and design review.
  2. Black-box attack probes against the running API (Octane/Swoole, `APP_ENV=staging`, debug off).
  3. Load tests with k6.
  4. Database checks with 2 million rows and `EXPLAIN ANALYZE` under row-level security.
- **Fixes:** #359 (this PR). Later items: #360, #361, #362, #363, #364 (sign-up bot protection), #182 (external pentest), #294 (retention).
- **Not a substitute for the external penetration test before public launch (#182).**

## Summary

| Severity | Found | Fixed in this PR | Tracked for later |
|---|---|---|---|
| High | 3 | 3 | — |
| Medium | 10 | 10 | — |
| Low | 8 | 7 | 1 |
| Infrastructure (design) | 9 | 3 | 6 |

After the fixes, all **31 attack probes** pass (`tests/security/api_probe.py`). Every finding has a regression test (`tests/Feature/SecurityRegressionTest.php` and others), so it can't come back unnoticed.

What held up from the start:

- **Tenant isolation.** No cross-workspace read, write, update or delete on any endpoint. This held even with the Eloquent scope removed, thanks to RLS.
- **Webhook signatures.** Secret and HMAC checks, constant-time compare.
- **SQL injection.** Every query uses bindings, and every identifier is validated.
- **Mass assignment.**
- **Sign-in.** Lockout can't be bypassed with `X-Forwarded-For`.
- **Error bodies.** No internals leak.

## Findings

### High

| ID | Finding | Evidence | Fix |
|---|---|---|---|
| F-01 | **Privilege escalation through custom roles.** A member whose custom role had `workspace.roles.manage` could edit **their own role** to add any permission (numbers, team management). An admin could create roles with powers admins lack. A member manager could give out roles above their own. | Probe: role editor PATCHed own role → 200 | Grant ceiling: nobody grants, assigns or removes beyond their own permissions; nobody edits or deletes the role they hold (`ManageRoles`, `ChangeMemberRole`). |
| F-14 | **App runtime could switch RLS off.** The API logged in as the table owner and used `SET ROLE` only to narrow itself. With SQL access (an injection or RCE), `SET ROLE NONE` would return to the owner, which bypasses RLS. | Design review | Separate logins: `trik_api` (NOINHERIT, can only become `trik_app`), `trik_owner` only for migrations and the scheduler (`infra/postgres/roles.sql`, runbook). Test proves `SET ROLE NONE` leaves zero access. |
| L-01 | **Message log did a full scan.** Listing a number's messages scanned every row of the partition: **2,446 ms at 2M rows**. | `EXPLAIN ANALYZE` | Index `(number_id, created_at desc, id desc)` → **0.2 ms**. |

### Medium

| ID | Finding | Fix |
|---|---|---|
| F-02 | Unverified emails could connect WhatsApp numbers and send (throwaway accounts, spam). | `verified.email` middleware on all WhatsApp routes (`email-not-verified`). |
| F-03 | `Idempotency-Key` on sign-in cached the **response with the token** in Redis for 24 h. | Idempotency only for signed-in callers; guest responses are never stored. |
| F-04 | No body size limit: a 3 MB webhook went through routing and DB work (jsonb bloat, memory DoS). | `LimitRequestSize` runs first: 1 MB for webhooks, 2 MB for the API → `413`. Also enforce at the edge. |
| F-05 | Webhook endpoints had no protection against floods of junk. | Invalid deliveries are counted: per IP for unknown or unsigned requests, **per number** for a wrong secret, 60/min, then `429`. A wrong secret on one number never blocks the provider's shared IP for everyone (found during the load test). |
| F-06 | Provider ids went unvalidated into provider URLs (`123/../../me?fields=…`). | Meta ids must be numeric; BSP channel ids must be slugs. |
| F-07 | CORS used framework defaults: wrong paths (`api/*`), no credentials, so the web app couldn't use cookies. | `config/cors.php`: only `FRONTEND_URL`/`CORS_ALLOWED_ORIGINS`, credentials on, explicit headers. |
| F-08 | Tokens never expired; a password reset left browser sessions signed in. | Tokens expire after 60 days and are pruned daily; a reset deletes all sessions too. |
| F-09 | Lockout was per email+IP only (distributed guessing). A missing account skipped the hash, a timing oracle for which emails exist. | Plus a per-account limit (20 failures/hour across IPs); always one hash check. |
| R-01 | **Lost wake-up:** if the queue push failed after a webhook was stored, the delivery waited until the next one for that workspace. A Redis restart could strand deliveries. | `AcceptWebhook` still answers 200; `whatsapp:sweep` (every minute) wakes stranded drains. |
| R-02 | Duplicate sends were possible if a send job was redelivered while still running. A message whose job was lost stayed `queued` forever. | A lock per message and per broadcast chunk. The sweeper marks messages queued over 2 h as `failed` (`dispatch-lost`) so the seller sees them. It never resends automatically. |

### Low

| ID | Finding | Status |
|---|---|---|
| F-10 | Bad `contact` filter → 500 | Fixed: 422 |
| F-11 | No security headers | Fixed: nosniff, DENY framing, no-referrer, CORP; HSTS over HTTPS |
| F-12 | App role could read/write the `migrations` table | Fixed: revoked |
| F-13 | Unlimited workspaces per user (abuse) | Fixed: 10 owned (configurable) |

### Database and load

Measured on this machine: 2 shared vCPU, PostgreSQL 19, Octane with Swoole (2 workers), k6 on the same box. Production servers are larger; treat these as **lower bounds**.

| Check | Result |
|---|---|
| Webhook intake (Laravel) | **~250 req/s**, p95 110–160 ms at 200–250 req/s; saturates beyond that. ≈ 125 req/s per vCPU. |
| Batch drain (1 worker) | **17,040 deliveries in 6.2 s ≈ 2,700/s** (fixed query count per batch) |
| Status batch update, 500 rows, 2M-row partition | **18–28 ms** (index nested loop), ≈ 20k statuses/s per core |
| Bulk insert into a partitioned table | 2M rows in 43 s ≈ 47k rows/s, with 4 indexes |
| Message log page (2M rows) | 2,446 ms → **0.2 ms** after L-01 |
| Contact filter (2M rows) | 0.2 ms (existing index) |
| RLS overhead | A one-time filter per partition; no per-row cost visible in plans |

Changes from the load work:

- **Fill factor 85** on message and broadcast partitions, so status updates stay HOT (no index writes, less bloat).
- **Explicit `provider_message_id is not null`** in the batch update. The partial index then stays usable whatever the planner estimates (a `generate_series` probe planned a 2.5 s hash join; the real `VALUES` path takes 20 ms).
- **ADR 0010 trigger corrected with measured numbers:** move intake to Go when the pilot server passes ~500 deliveries/s sustained or ack p95 > 200 ms. The < 50 ms p99 target applies to the Go intake.

## Infrastructure review (ADR 0011)

| Topic | Risk | Action |
|---|---|---|
| Database logins | Runtime had owner rights (F-14) | **Fixed**: three roles, runbook `docs/runbooks/database-roles.md`, plus timeouts on `trik_api` |
| Exposed dev ports | Compose bound DB/Redis/etc. on all interfaces | **Fixed**: `127.0.0.1` only |
| Health check | Dockerfile used `curl`, which the FrankenPHP image lacks: the container would always be unhealthy | **Fixed**: PHP probe |
| Edge | No WAF, DDoS shield or edge body limits | #360: Cloudflare in front of `api`/`app`, Caddy `request_body max_size`, only 443 open |
| Redis | One instance for cache, queue and locks, no persistence → queued jobs lost on restart (sweeper limits the damage) | #361: AOF `everysec` for the queue Redis, separate cache instance, `maxmemory-policy` per role |
| `APP_KEY` | Encrypts provider credentials. Losing it loses every number's credentials; leaking it exposes them | #362: secret store, offline backup, rotation with `APP_PREVIOUS_KEYS` |
| Single pilot server | Single point of failure | Accepted for the pilot; backups and restore drill (#352), replica after the pilot |
| Retention | Raw webhooks kept 2 months; messages kept indefinitely (PDPL) | Covered by #294; decide message retention before launch |
| Supply chain | Actions pinned by tag | #363: SHA pins + Dependabot for actions, composer, npm |
